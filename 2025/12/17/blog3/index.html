    ⑤AnnotationInvocationHandler

    前面说到过反序列化入口需要有readObject,这个类完美的重写了readObject方法，同时这个readObject方法还可以串联起我们的构造链。

    首先利用反射强行实例化

    这里的Retention.class 它告诉 Handler：“你是用来处理 @Retention 这个注解的。” 这也决定了后续 Handler 会去检查 Map 里有没有 key 叫 "value" ，这也就是我们之前给map传入value的原因

    以上是构造方法，Object payload = constructor.newInstance(Retention.class, transformedMap); 就是这步传入Retention.class, transformedMap，即 this.memberValues=transformedMap 。那么在反序列化时触发readObject，AnnotationInvocationHandler会遍历memberValue（也就是之前的transformedMap），它拿到了我们构造的那个 Entry：key=”value”, value=”uselessString”。

    查阅规则： 它去查看 Retention.class 的定义，发现确实有一个叫 value() 的方法，且其返回类型应该是 RetentionPolicy（枚举）。

    对比现状： 它看了一眼 Map 里的 value，发现是一个 String类型

    于是调用memberValue.setValue（）进行修正，会触发TransformedMap修饰器的checkSetValue，因为 TransformedMap 在装饰 HashMap 时，不仅装饰了 Map 本身，还装饰了它的 entrySet()。当我们遍历 Map.Entry 并调用 setValue 时，实际调用的是被修饰过的 MapEntry.setValue，这个方法内部会回调 TransformedMap 的 checkSetValue.可以类比TransformedMap这个修饰器包裹着map，任何修改会经过这个修饰器。这个修饰器会返回return this.valueTransformer.transform(value)。终于，心心念念的transform来了，反序列化链成立！！

    反序列化

    为什么是Retention.class，以及为什么Key 必须是 “value”

    上文中提到，AnnotationInvocationHandler类中的readObject上触发了setValue方法，而触发这个方法的对象名是memberValue。有意思的是memberValue是在AnnotationInvocationHandler类构造方法中进行赋值的

    Class[] var3 = var1.getInterfaces();先获取var1的接口

    可以看到，想要赋值成功就需要满足三个条条件

    • var1.isAnnotation() => 检查var1是否是一个注解（类似@Override）
    • var3.length == 1 => 检查var1的接口数量是否为1
    • var3[0] == Annotation.class => 检查这个唯一的接口是否是Annotation.class

    所以构造方法应该传入一个注解类型的类对象,调试后可以知道Retention.class符合这个条件，当然我目前看到还有Target.class。

    对于key为value,在AnnotationInvocationHandler类的readObject上会遍历传来的Map,想要执行var5.setValue()，就要通过条件!var7.isInstance(var8) && !(var8 instanceof ExceptionProxy)，当然并且要满足var7 != null，那么var7是(Class)var3.get(var6);，一步步往上拨开，var5.getKey()的值赋给var6,var3就是传入的Retention.class

    看看Retention.class中存在一个方法—value，那么一切都成立了，也就顺利的反序列化了。
