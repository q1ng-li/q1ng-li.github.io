由于之前的漏洞已经在原作者的代码中进行了patch,于是上网并结合ai找到了原生漏洞代码，这里也就不是单纯解出这个flag,而是复现出这个漏洞。

可以看到 return type(str(name), (), pickle.loads(gzfile.read()))这行代码中pickle.loads，有python反序列化的味道了。那么就利用题目给的docker进行复现了。接下来我们应该清楚怎么样可以调用_load_data函数

构造的pdf如下

说实话，第一次看到这个pdf有点懵，毕竟之前看到的都是经过源码渲染的。简单解释一下这个源码，首先%PDF-1.7是定义pdf规范；接着1 0 obj 表示第一个对象，定义了一个目录（Catalog）,以及引用了页面对象（通过/Pages 2 0 R）；endobj表示结束；后面其余对象分别定义了字体，大小等等；最后，xref(交叉引用表) 定义了每个对象在文件中的字节偏移量（例如 0000000010），trailer指出根对象是 1 号对象，并包含文件结束标记 %%EOF。

不过对于这个pdf最重要的5 0 obj，/Encoding 字段通常用来指定字体的编码方式，但这里的值设置为/Adobe-GB1-0，意图调用_load_data函数去加载这个未知的编码。可惜我不清楚怎么去弄断点来看这个结果，只能借鉴官方的图片

此时的调用栈为

可以看到成功调用了_load_data，传入的参数是Adobe-GB1-0。name=”Adobe-GB1-0”,接着去除空字节，filename=”Adobe-GB1-0.pickle.gz”,系统环境变量 CMAP_PATH 指定的路径，或者默认的 /usr/share/pdfminer/;接着进入for directory in cmap_paths循环，假设directory是/usr/share/pdfminer/，path拼接为/usr/share/pdfminer/Adobe-GB1-0.pickle.gz，一旦找到文件，就先利用gzip打开文件，再将文件内容进行反序列化。那么接下来我们就要控制pickle文件的路径 ，可以看到源码中没有对name进行过滤，那么我们可以利用目录穿越，比如/Encoding /../../../../../../../../../../../evil来控制路径，但是.和/不会被当成字符串，那么就配合16进制进行编码 /#2e#2e#2f#2e#2e#2f#2e#2e#2f#2e#2e#2f#2e#2e#2f#2e#2e#2fapp#2fa 首先解释一下，第一个/表示界定符，后面的#2f是因为PDF ISO 32000 标准明确规定，Name Object 的十六进制转义符只能是 #

我们一点一点来看，首先build_pdf函数中就是生成一个pdf;build_gzip_with_extra函数利用了FEXTRA（拓展字段），Gzip 标准规定：解压程序在读取到 FEXTRA 标志时，会读取长度字段，然后跳过指定长度的数据（即跳过整个 PDF），直接去解压后面的data。当然，本质上与官方的原理相同。
