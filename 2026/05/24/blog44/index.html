代码审计

step1 寻找sink点

首先就是寻找一些危险函数，比如eval,spawn,exec等。通过搜索spawn,发现在12307\services\print_spooler\worker.py下的def run_driver(program, argument)方法中存在命令执行

使用 os.posix_spawn 启动子进程。如果参数可控，便可以执行任意命令

step2 回溯调用堆栈

当我顺利追溯到def main()下的代码

发现handle需要处理的是item[1],而item = redis.command(“BRPOP”, “rail:spool:requests”, 1) 老实说确实看不懂这行代码，涉及到redis的操作。

这里简单了解一下，这里把redis当作一个中转箱，中转箱的名字叫做rail:spool:requests,项目中有两个程序：

depot_layout：负责往中转箱里放任务
print_spooler：负责从中转箱里取任务并执行

item[1]就是放任务中的json.dumps(ticket)，也就是说接下来的思路就是看看JSON 格式的 ticket中有没有可以用户输入的

接下来就是追溯到depot_layout/app.py#spool_device() ，可以看到ticket格式

其中”driverProgram”和 “driverArgument”参数来自print_plan，继续往上追print_plan = context.get("printPlan") if isinstance(context.get("printPlan"), dict) else {}看看context是哪里传来的，可以看到来自 def collect_device(device_ref, station_code, context);继续往上，在depot_layout.do_POST()中 context = data.get("context") if isinstance(data.get("context"), dict) else {},可以知道是通过前端context参数传来的；最后在 settlement_worker.bridge_preview()

step3 构造gadget chain

Gadget Chain

关键数据流

用户控制的是：

{
“driverProgram”: “/usr/bin/base64”,
“driverArgument”: “/flag”
}

它最开始藏在：

carrierSeal.payload

然后在 receipt_signer/app.py 中进入 print_plan：

print_plan = {
“driverProgram”: str(render_view.get(“driverProgram”, “”))[:160],
“driverArgument”: str(render_view.get(“driverArgument”, “”))[:160],
}

接着被写入 Redis：

redis.command(“SET”, f”rail:receipt:seal:{receipt_id}”, json.dumps({
“print”: print_plan
}))

之后 settlement_worker 取出：

print_plan = ctx[“mint”].get(“print”)

再传给：

bridge_preview(device_ref, context, print_plan)

bridge_preview() 构造内部请求：

最终 print_spooler.handle() 取出：

program = str(ticket.get(“driverProgram”, “”))
argument = str(ticket.get(“driverArgument”, “”))

进入 sink：

run_driver(program, argument)

也就是：

run_driver(“/usr/bin/base64”, “/flag”)

最终 gadget 表达式

carrierSeal.payload.driverProgram = “/usr/bin/base64”
carrierSeal.payload.driverArgument = “/flag”

触发后实际执行：

/usr/bin/base64 /flag

为什么能过校验

print_spooler.handle() 有白名单校验：

accepted = route.get(“acceptedPrograms”)
program in accepted

HGH 的设备链对应：

device-map.json 中 profile-delta-closeout 允许：

/usr/bin/base64

所以 /usr/bin/base64 /flag 可以通过校验。最终输出会进入渲染结果，通过 reconciliation 结果接口读到
