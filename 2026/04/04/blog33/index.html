Sign复现

简单看看这题解出来的最多

打开是一个查询页面，提示require a valid signature,我们抓包看看，我们发现每查询一次，服务先返回一个/api/sign接口，再实现查询功能

这个限制导致我们无法对一个包重复发送，因为每一个包都对应着一个签名

经过一系列测试，猜测后端语句为

但是自己确实没有构造出来可行的payload,菜还得多练啊。我先尝试可否逆向出签名的算法

不过上次学习js逆向还是上学期暑假了。快一年没碰这玩意了，并且当初学得还是基础，这里得好好捡起来了

看到app.js中 _s[i]进行了base64混淆，解密看看

页面源代码可以看到，当用户点击Search时，js监听触发doQuery函数

跟进该函数，发现调用了loadWasm()，我们可以下个断点，调试一下，目前并不清楚loadWasm的作用；接下来跟进getSignMaterial(),大概是获取计算sign的所需参数,_d(0)就是 /api/sign, 也就是fetch这个路径，最终就返回了{algo,nonce,salt,seed,ts}这五个参数；接下来是__suPrep,变量pre经过计算得到，然后secret2 经过函数unscramble(pre,nonce,ts)计算得，接着mixed经过 mixSecret(secret2, probe, ts) 计算得到，最后sig又经过__suFinish得到

目前逆向到这，加密过程都比较熟悉，唯一不明白的是两个函数，这两函数哪来的，在app.js根本找不到

于是询问了AI大人，原来

这两个函数并不是浏览器自带的，也不是这段 JavaScript 原生定义的，它们是 通过 WebAssembly (WASM) 注入到全局作用域（window 或 globalThis）中的；而对于WASM，是一种二进制指令，人类不可读，但是js通过fetch获取.wasm二进制流

很好，文件中也给了我们crypto1.wasm和crypto2.wasm，我们似乎可以借此来还原整个计算sign的算法(ai似乎跃跃欲试，那就决定是你了)

解疑

老实说前面的流程还都比较正常，可是发现caddy是由root用户启动的，并且暴露了配置文件路径可以联想到curl修改配置文件的思路还是不理解，另外caddy又是什么，在这个站点中充当什么身份？

Caddy是一个现代化的 Web 服务器和反向代理，类似Nginx，Apache。其功能有静态页面托管，请求处理，反向代理等等。

默认管理站点 http://127.0.0.1:2019,http://127.0.0.1:2019/config/导出整个配置

caddy-api文档：https://caddyserver.com/docs/api

我们看到/etc/caddy/caddy_config.json（与http://127.0.0.1:2019/config/内容相同），Caddy监听80端口，即用户访问http://target:80,后端服务器（Grafana）监听3000端口；而上面提到的2019端口是Caddy的大脑
